---------------------------------------------Git Tags----------------------------------

Git tag serves as a static, immutable pointer to a specific commit in your repository's history.
Unlike branches, which are designed to move and evolve with new commits, a tag always points to the same commit it was originally created for.

Tags are primarily used to mark significant points in a project's history, most commonly for:
Releases, Milestones, Historical Restore Points

Lightweight Tag -- its like a bookmark, just a name for a commit, quick and simple, but does not store extra information.
git tag v1.0 -- after a commit add this tag and mark a milestone in your project.
git tag <tagname>

Annotated Tag -- stores your name, the date, and a message,most recommended as it stores more data.
git tag -a v1.0 -m "Version 1.0 release" --> write a message too.
git tag -a <tagname> -m "message"

git tag v1.1 1a2b3c4d -- tag a old commit by specifying its hash name
git tag <tagname> <commit-hash>

git tag -- to list all tags

git show <tagname> -- show tag details

*********Pushing commits with git push does not push your tags, You must push tags explicitly as shown above*****************

git push origin v1.0 --tags exist only on your local computer,If you want others to see your tags, you need to push them to your remote repository.
-- push all your tags manually/explicitly to the remote repo to make it public

git push --tags -- to push all your local tags all at once

git tag -d v1.0 -- to delete a tag locally

git push origin --delete tag v1.0 -- to delete tag in remote repositories

git tag -f v1.0 <new-commit-hash>
git push --force origin v1.0 -- If you need to move a tag to a different commit and update the remote, use --force

git tag -d <tagname> -- to delete a already existing tag
git push --force origin <tagname> -- this will push and change all the tags remotely for everyone

-------------------------------------Git merge----------------------------

-- To combine the changes from one branch into another, use git merge.
-- Merging in Git means combining the changes from one branch into another, this is how you bring your work together after working separately on different features or bug fixes.

-- switch to brach you want to merge into, and then use git merge tp merge two branches
eg: git switch master

git merge new_branch -- merge the new_branch to the master

-- only commited changes / files will be merged, staged will not be merged
-- Always commit or stash your changes before starting a merge.
-- Regularly merge from the main branch into your feature branch to minimize conflicts.
-- Read and resolve conflicts carefully—don't just accept all changes blindly.
-- Write clear and descriptive merge commit messages.

git merge --abort -- abort a merge
********************Resolve a conflict and complete the merge: Edit the conflicted file(s), then git add file and git commit******************
Fast-forward merge -- A fast-forward merge is possible only when the "target" branch (e.g., main) has no new commits since you branched off it to create the "feature" branch. 

git merge --ff-only <branch-name> --This ensures that Git only merges if a fast-forward is possible. If the branches have diverged, it will abort the merge.

git merge --no-ff <branch-name> --This forces Git to create a merge commit even if a fast-forward is possible, which preserves the historical record of the branch's existence. 
-- always use --no-ff to preserve commits and doesn't just move the pointer forward


git merge --squash branchname -- If you want to combine all the changes from a branch into a single commit (instead of keeping every commit).
-- This is useful for cleaning up commit history before merging.

git merge --abort -- If you run into trouble during a merge (like a conflict you don't want to resolve), you can cancel the merge and go back to how things were before 

*****************************************Merge Conflict****************************************

-- happens when changes in two branches touch the same part of a file and Git doesn't know which version to keep.
-- edit the file having file conflict and review it and then stage it and then commit and later merge it.

git checkout master -- switch to the branch where you want to merge the changes

git merge hello-world-images -- now start merging the branches -- The merge will fail, as there is conflict between the versions 

git status -- to check where the conflict is happening, 

fix the conflicts by editing the files where conflict happened

after editing -- stage the changes again

git add <file_name> -- stage the file where conflict is fixed.

git commit -m "conflict fixed" --- now commit the file where you fixed the merge, only after you commit here, the merge will complete, untill here the merge will stop.

git branch -d hello-world-images -- now delete the merged branch, as you already recorded all the changes here.

----------------------------------------------Git Rebase-------------------------------------------------

-- git rebase, especially the interactive mode (git rebase -i), gives you a powerful "second chance" to review, edit, reorder, squash, or drop commits, 
creating a cleaner, linear commit history by replaying your changes on a new base, essentially rewriting history for a pristine timeline before merging. 

-- It is a process that moves a series of commits to a new base, creating new commits for each one, but it offers an interactive mode

-- is considered dangerous primarily because it rewrites the commit history. This can cause significant issues, especially when used on shared or public branches

-- Rebasing moves or combines a sequence of commits to a new base commit.
-- Rebasing can make your commit history easier to read by avoiding unnecessary merge commits.

Keep a clean, linear project history
Avoid unnecessary merge commits
Combine multiple commits into one
Edit or reorder commits

git checkout feature-branch
git rebase main -- this creates new base/commit stash, where you can edit and rewrite the commit, this will let you stash your feature branch commits
on main branch, this does not merge instead extends the commit history.

-- The result is a new, linear history where it appears as if you started your feature development from the most recent point in the target branch's history. 
Your original commits are gone and replaced by new ones with new commit hashes

-- This differs from using git merge, which would create a special "merge commit" that ties the two histories together while preserving both histories intact [1]. 
Rebasing creates a cleaner, more linear project history. 

-- do not rebase on the shared branch, this will disrupt everything.

git rebase -i HEAD~3 -- interactive mode, more control.

git add fixed_file.txt
git rebase --continue -- fix conflict and continue rebase

git rebase --abort -- stop rebasing

git rebase --skip -- skip particular commit and move ahead with rebasing.

----------------------------------------Git LFS (Large File Storage)-----------------------------------------------------------------

--- is an extension for Git that helps you manage large files (like videos, images, or datasets) efficiently.
--- Instead of storing big files directly in your repository, 
--- LFS stores a small pointer file in your repo and keeps the real content on a separate LFS server.

-- This keeps your repository fast and small, even if you work with huge files.
-- Everyone who clones the repo gets the pointer, and Git LFS fetches the real file content as needed.

git lfs install -- to install LFS

git lfs track "*.psd" -- tell git to track which files using LFS

-- When you track a file type with LFS, Git adds a rule to the .gitattributes file. This tells Git to use LFS for those files.

Add files as usual: git add largefile.psd
Commit: git commit -m "Add large file"
Push: git push origin main
The actual file data is stored on the LFS server, while your repo contains a pointer file.

-- If you clone or pull a repo with LFS files, Git will download the real content from the LFS server (if you have LFS installed).

git lfs ls-files -- to see which all files are managed by LFS

git lfs untrack "*.psd"
git add .gitattributes -- to untrack the LFS files.

git lfs pull -- to pull lfs pointer and lfs files from remote repo

CI/CD stands for Continuous Integration and Continuous Deployment/Delivery.

It means your code is automatically tested and deployed every time you push.
Find bugs before they reach users
Deploy changes faster and more safely
Reduce manual steps and mistakes
Get quick feedback on every push

Every time you push code to your Git repository:

The CI/CD service (like GitHub Actions or GitLab CI) detects the change
It runs tests, builds your project, and can deploy automatically
If something fails, you get notified right away

[Developer] --push--> [Git Repository] --triggers--> [CI/CD Pipeline: Test, Build, Deploy] 

CI/CD helps catch bugs early and speeds up delivery. Even small projects can benefit from automation!

Here are some important terms:

Workflow: A series of jobs that run together
Job: A group of steps that run together
Step: A single task, like checking out code or running tests
Runner: The computer/server that runs your jobs
Trigger: Decides when your workflow runs
Environment Variables: Settings for your workflow
Secrets: Passwords or API keys

git commit -m "Update docs [skip ci]" -- to skip build

.yml file structure

name: Sets the workflow's display name in GitHub.
on: Decides when the workflow runs (here: every push).
jobs: Groups together steps that run on a runner.
build: The name of this job (can be anything).
runs-on: Picks the type of server (here: Ubuntu Linux).
steps: Each step does one thing, like checking out code or running tests.
uses: Uses a pre-made GitHub Action (here: checks out your code).
name: (under steps) Gives a step a label.
run: Runs a shell command (here: npm test to run tests).

--------------------------------------------------------Git hooks----------------------------------------

Git hooks are scripts that run automatically when certain Git events happen, like making a commit or pushing code.
Hooks help you automate repetitive tasks, enforce coding standards, and catch problems early.

For example, you can:

Run tests before every commit or push
Check code style automatically
Block bad commit messages
Enforce rules for everyone on your team

Hooks are stored in .git/hooks inside your repository.

There are many types of hooks, but the most common are:

pre-commit
commit-msg
pre-push
pre-receive
post-receive
