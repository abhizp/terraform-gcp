Docker commands:

Dockerfile: has all the information required to build a container.
docker file is in the same directory as the env file, requirements and the app's directory.
execute docker build command from the directory where your docker file is present.

docker build . --> execute this in the same directory where dockekfile is present.
docker build -t "container_name" . --> to give a tag to the docker container

docker images -- to list all the images in the local host

-- the application is built and is in the form of a image now, it will have image id.

To run your application:

docker run <image_id>

to run interactively:

docker run -it <image_id>

to map/bind the docker's port with the host's port:

docker run -p 8000:8000 -it <image_id>

docker run -d -- run docker in detached mode.

docker run --help -- for more arguments

Multi-stage docker image:

distroless image: -- no OS image, bare minimum

Bind mounts: -- you have to give a full path to directory on the local host and this bind it with container's directory, 

docker run -d \
  -it \
  --name devtest \
  --mount type=bind,source="$(pwd)"/target,target=/app \
  nginx:latest
  
source can be any directory on the local host

Bind mounts in Docker are a method for mapping a file or directory on the host machine to a directory within a container. 
Unlike Docker volumes, which are managed by Docker in a specific storage area, 
bind mounts rely on the specific directory structure and absolute path of the host's filesystem

They are highly effective for development environments because changes made on the host are immediately reflected in the container. 



Volumes:

docker volume ls -- to list all the running volumes
docker volume create <volume_name> -- to create a new volume
docker volume inspect <volume_name> -- to inspect the details of volume, get all details
docker volume rm <volume_name> -- to delete a specific volume
docker volume prune -- to remove all unused volumes

one volume can be attached to multiple containers

docker run -d --mount source=myvol2,target=/app <image_name/id> --to attach a volume to a image.

docker ps -a -- to get the list of all the containers on the host
docker ps -- to get the list of only running containers

docker inspect <container_name> -- to get all the details of the containers

stop the container before deleting the volume

docker exec -it <container_identifier> <command> -- to run few commands in already running docker container
docker exec -it <container_identifier> /bin/bash -- this will open a interactive shell terminals

docker network ls -- to list out all the network
docker network rm <network_name> -- to remove a network

docker network create <network_name> -- to create a network -- by default bridge network will be created.
The containers inside the same bridge can talk to each other but can not talk to other containers on diff bridge

docker run -d --name <container_name> --network=<network_name> <image> -- to run a container in certain network

docker run -d --name <container_name> --network=host <image> -- the container will use same IP address as the host, container is binded with the host's IP address

Docker Volumes:

Docker uses layered architecture

-- when you create docker container out of docker image, the layers formed from docker image remain the same, they are immutable.
-- docker creates a write layer on container where all the activity happens, here is where writes happens any files or logs generated by container are stored here.
-- this layer/files on this layer are deleted/gone once the container dies.

Copy-on-Write (CoW):
-- Copy-on-Write (CoW) is an optimization strategy used by Docker to share storage space and maximize performance by delaying file duplication until a modification is explicitly made.
-- Docker separates filesystems into structured, stacked layers handled by a storage driver like overlay2

-- image Layers (Read-Only): The base instructions (FROM, RUN, COPY) form immutable, permanent layers.
-- Container Layer (Thin Writable): When you run a container, Docker injects a unique, thin read/write (R/W) layer on top.

┌─────────────────────────────────┐
│  Container Writable Layer (R/W) │  ◄── Modified files land here
├─────────────────────────────────┤
│     Image Layer 2 (Read-Only)   │
├─────────────────────────────────┤
│     Image Layer 1 (Read-Only)   │  ◄── Shared among other containers
└─────────────────────────────────┘

Reading a file: The container reads directly from the underlying read-only image layer. No duplication happens.
Modifying a file: The first time a file needs to be modified, Docker copies the complete file from the lower image layer up into the thin writable layer. The change is then applied only to this copy, leaving the base image untouched.
Creating a file: The file is written directly into the thin writable layer.

Use docker mount command to mount the local directory to the image.

volume mounting:
to mount the volume from /var/lib/docker's volume directory to the image.

Bind mounting:
to bind mount the volume from anywhere in local system to the images

Docker storage: drivers manage the lifecycle of stackable image layers and the thin, writable container layer using a copy-on-write (CoW) strategy. 
They enable multiple containers to share the same underlying read-only image data while maintaining their own unique internal state.

A Docker volume driver (or volume plugin):
is a software component that abstracts the underlying storage infrastructure from your containers, 
enabling data persistence across different hosts, network shares, or cloud providers
-- While Docker storage drivers (like overlay2) handle ephemeral container image layers, volume drivers explicitly manage persistent data

Types of Volume Drivers:
local (Default): Handles storage natively on the Docker host machine. On Linux, data is stored under /var/lib/docker/volumes/. It can also be configured to natively mount Network File Systems (NFS) or CIFS/Samba shares.
Cloud Block Storage: Integrates with managed cloud volumes—such as AWS EBS via plugins like REX-Ray or Portworx—allowing volumes to automatically detach and reattach if a container moves to a different host.
Shared Cloud Filesystems: Links containers directly to managed network storage systems like AWS EFS or Azure File Storage

1. Create a Volume with a Specific Driver:
docker volume create --driver local my-local-vol

2. View Active Drivers:
docker volume ls


The default local driver is incredibly versatile and allows you to attach remote filesystems directly without external plugins. 
To supply these complex parameters, use the explicit --mount flag instead of -v:

docker run -d \
  --name web-app \
  --mount 'type=volume,src=nfs-volume,dst=/app/data,volume-driver=local,volume-opt=type=nfs,volume-opt=device=:/path/to/dir,"volume-opt=o=addr=192.168.1.50,rw,nfsvers=4"' \
  nginx
